## 4. 逐项实施计划

### 1. 深浅主题切换时封面与头像不抖动

**问题分析**

- 当前主题过渡会克隆 `#root`，再将图片、视频、`.artwork` 与 `.avatar` 的 `DOMRect` 写入快照。虽然快照层已禁用动画，但实际页面与克隆页面的媒体几何没有一套显式的过渡合同。
- 封面、圆形歌手头像、小黑胶中心封面和展开播放器封面分别处于 grid、flex、圆形裁切和全屏层中。主题变量变化、快照尺寸回写或对象适配发生在不同帧时，用户会看到图片短暂跳位。

**实施方案**

1. 为主题过渡建立“媒体几何只读”约束：在切换前读取源节点的边界、`object-fit`、`object-position`、transform 和裁切参数；过渡期间快照只用于旧主题画面，不能反向改变活页面布局。
2. 检查快照写入宽高是否会改变 grid/flex 子项的布局。必要时改为仅对快照节点使用独立的冻结样式或 CSS 自定义属性，而不是以会参与正常流布局的方式重设尺寸。
3. 将禁用过渡的选择器覆盖到所有实际媒体表面（普通封面、头像、播放器中心封面、展开播放器封面），但仅在主题 reveal 生命周期内生效；正常 hover 的轻微反馈保持不变。
4. 用 DOMRect 采样主题切换前、动画中、结束后三个时点，区分“快照层移动”和“活页面移动”；修复以活页面无布局位移为准，不用延长动画掩盖问题。

**拟改文件**

- `src/App.tsx`
- `src/App.css`
- 按实际可测试边界补充主题过渡定向测试或开发态 DOM fixture

**验收条件**

- 深色 → 浅色、浅色 → 深色，普通封面、歌手头像、小黑胶中心封面和展开播放器封面的中心点/宽高在主题 reveal 中漂移不超过 `1 CSS px`。
- 图片保持原来的 `object-fit` 与裁切，不闪白、不重新加载、不改变页面滚动位置。
- `prefers-reduced-motion` 下无额外位置动画；正常状态下卡片 hover 效果仍有效。

**状态**：已实施，待整轮回归。

### 2. 没有歌词时的歌词按钮 tooltip

**问题分析**

- 当前根部状态已经区分“加载中”“请求失败”“确认无歌词”，并在 `PlayerBar` 中生成“这首歌暂无歌词”的标签。
- 禁用原生 `button` 的 hover/title 行为在 WebView 中不应被当作可靠 tooltip 承载；用户需要的是固定、精确的“暂无歌词”提示，而不是依赖浏览器对 disabled 元素的实现差异。

**实施方案**

1. 将歌词 action 的显示标签、无障碍名称与 tooltip 状态分开：确认无歌词时 tooltip 精确显示“暂无歌词”。
2. 为禁用态增加不会影响点击/焦点语义的 tooltip 承载层，保证 hover 到图标区域即可提示；按钮本身继续禁用，不能借 tooltip 变成可点击元素。
3. 保持状态边界：加载中不是“暂无歌词”；请求失败不是“暂无歌词”；未播放时仍提示先播放歌曲。切歌后不复用上一首的 tooltip 状态。
4. 同一歌词动作以后将在第 5 项复用于展开播放器，两个入口必须使用同一套文案和可访问性语义。

**拟改文件**

- 相关组件测试

**验收条件**

- 有 timed/plain 歌词：按钮可用，tooltip 为“打开歌词”或“关闭歌词”。
- 加载、失败、未播放三种状态不被错误归类为“暂无歌词”。

### 4. 修复音量浮层竖向滑条的异常外层着色

**问题分析**

- 用户截图显示主播放器音量浮层外出现异常颜色区域。当前实现同时使用 `writing-mode`、`direction: rtl` 与 `appearance: slider-vertical`，WebKit 原生 vertical range 的背景绘制可能脱离了定制轨道。
- 主播放器与展开播放器各有一套竖向 range 规则，尽管数值计算已收敛到 `SharedVolumeControl`，视觉实现仍可能出现不一致。

**实施方案**

1. 废弃依赖浏览器原生 `slider-vertical` 的渲染路径，统一使用明确 `appearance: none` 的受控轨道；用固定尺寸容器和旋转/坐标映射实现竖向视觉，禁止原生输入背景向浮层外溢出。
2. 保留 `SharedVolumeControl` 的单一音量值、静音恢复、百分比和 `aria-valuetext`，不拆出第二套 state。
3. 为紧凑与展开 variant 共用轨道、thumb、填充方向和禁用态规则，只由各自主题 token 决定颜色。
4. 校验鼠标、滚轮以外的键盘输入：顶部为 100%，底部为 0%，上/右增大，下/左减小；静音后从零以上拖动恢复声音。

**拟改文件**

- `src/VolumeControl.tsx`
- `src/App.css`
- `src/NowPlayingView.css`
- `src/VolumeControl.test.ts`

**验收条件**

- 轨道始终在浮层内，底部为 0%、顶部为 100%，thumb 与数值一致。
- 深浅主题和三种品牌色下均只有正确的轨道、进度与 thumb 着色。

**实施记录（2026-08-05）**

### 5. 主/展开播放器底部结构统一，添加“添加到歌单”入口

**问题分析**

- 当前主播放器底栏是“曲目信息 / 传输与进度 / 额外操作”三列；展开播放器的歌曲信息仍放在视觉区下方，队列在底部左侧，而“添加到歌单”在顶部 header，信息层级与主播放器不一致。
- 当前根部已有 `PlaylistPicker` 和 `playlistTrack`，展开播放器可打开它；主播放器没有同等入口。
- 用户要求展开播放器底部的歌曲名和歌词入口放左侧，播放队列留右侧，同时两个播放器的右侧都提供“添加到歌单”。

**目标结构**

```text
主播放器底栏
左：小黑胶 + 歌曲名/歌手       中：传输控制 + 进度       右：歌词、添加到歌单、队列、设备（仅 Windows）、音量

展开播放器底栏
左：歌曲名/歌手 + 歌词入口     中：传输控制 + 进度       右：添加到歌单、播放队列、音量
```

**实施方案**

1. 将展开播放器的 `now-playing-track-meta` 从视觉区移入其底部控制栏左槽位，使歌曲信息与主播放器的底栏语义一致；视觉区只承担封面/黑胶。
2. 为 `NowPlayingView` 接入根部歌词开关状态和回调。展开播放器的歌词按钮放在左槽位，点击继续调用根部唯一的 `toggleLyricsPanel`，不能在展开层创建第二份歌词 UI。
3. 将展开播放器 header 的“添加到歌单”移除，改放到右侧控制槽。主播放器右侧新增同一入口，使用现有 `ListPlus` 图标、中文 tooltip 和根部 `PlaylistPicker`。
4. 展开播放器的队列按钮继续放右侧，调用既有 `toggleQueuePanel`；主/展开的队列状态、列表和浮层保持单例。
5. 在 1280px 最小桌面宽度内固定三列的最小宽度/截断规则：曲名可省略，控制区不压缩，右侧 action 不换行或重叠。图标按钮、焦点和 disabled 语义与现有播放器一致。

- `src/NowPlayingView.tsx`
- `src/App.css`

- 展开播放器左侧可见歌曲名、歌手和歌词入口；右侧可见添加到歌单、队列、音量。主播放器右侧新增添加到歌单且队列仍在右侧。

### 10. 歌手歌曲总数与全量歌曲操作

**问题分析**

1. 歌手详情进入时读取一次真实 `getArtistTracksPage()` 首页并复用结果，以服务端 `totalSize` 驱动标签文本。只有服务端已确认总数后才显示 `歌曲 (N)`；服务端真实返回零时显示 `歌曲 (0)`，加载中或失败时绝不伪造 `歌曲 (0)`。
2. 首页结果与现有懒加载列表共用同一缓存/请求世代，切换排序、歌手或服务器时必须失效并重新读取，不能产生双重首请求或把上一个歌手的总数带到新页面。

**全量集合与动作合同**

1. “播放”“添加到队列”“播放下一个”“添加到歌单”都必须从同一套 `collectAllArtistTracks` 流程取得结果：从 offset `0` 开始，按当前歌曲表排序（未排序时维持服务端默认顺序）串行读取所有分页，依据 `nextStart` 安全前进，使用 `appendUniqueArtistTracks()` 按稳定顺序去重，并在无进展、取消、换页或失败时停止。
2. 不能把当前可见页、已触发无限滚动的前几页或 `totalSize` 当作完整曲目集合。重复 ratingKey、最后一页不足一页、分页总数与本地加载数不同以及中途请求失败都必须有确定行为和明确反馈。
3. 主“播放”用完整集合替换播放队列，从第一首开始播放并关闭随机模式。"添加到队列"在现有队尾追加整批且不自动切歌；"播放下一个"将整批按原顺序插入当前曲目之后，不能倒序或打断正在播放曲目。
4. 在 `usePlayer` 内新增受控的批量队列 API，保持队列、当前 index、随机导航、持久化快照和预加载状态的一致性；页面组件不得访问或改写内部 queue ref。
5. 歌单选择器升级为接收一组已去重的 track rating key。批量写入必须经 Rust/Tauri：优先由一个显式的批量命令处理；若上游协议必须逐项请求，也只能在 Rust 端有序执行并返回真实的成功/失败/部分完成结果。前端不得并发直写 PMS、不得对部分失败显示“已全部添加”。
6. 四个动作在集合读取或写入期间应禁用重复触发，显示可访问的进行中状态；空集合、无服务器、请求失败和批量部分失败保留可重试入口且不悄悄改变队列。

**实施方案**

1. 把歌手歌曲的首批读取、真实总数、排序世代和完整集合读取抽到歌手详情的单一数据路径，保留当前列表的 IntersectionObserver 增量加载，避免与菜单操作竞争同一 loading ref。
2. 为歌手详情传入播放、追加、插入下一首和歌单选择所需的根部回调；主播放按钮与第 7 项 More 菜单只负责触发同一操作状态机。
3. 扩展 `usePlayer` 与其测试，定义批量追加/插入的当前曲目、空队列、随机和重复模式语义；不能借用 `playContext()` 造成无意替换队列。
4. 扩展 `PlaylistPicker`、`src/api.ts` 和 Rust command，传递经过本地去重的 ratingKey 列表并回报真实结果；保持每台服务器 scoped token 和现有错误转换，WebView 不接触 PMS 凭据。
