# Cadilume 当前开发清单与验收计划

更新日期：2026-07-29。

本文集中记录本轮用户反馈、根因分析、实现边界和验收顺序。代码调整应逐项对应本文，不以临时样式或固定延迟掩盖播放、歌词或布局问题。

当前状态：2026-07-29 进入第二轮桌面 UI 与歌词播放链路整改。每完成一个独立步骤，必须先更新本文记录实现与验证结果，再使用用户指定的 Chrome 按应用最小尺寸 `1280×820` 完成 Web UI 实测，确认通过后才进入下一步；本轮不调用 Codex 内部浏览器。

## 执行原则

1. 先保证能登录、能恢复窗口、能稳定播放，并让失败信息明确可见。
2. 播放器骨架、底栏和歌词容器必须保持稳定；曲目、封面或歌词变化不得推动整套 UI 上下跳动。
3. 整体视觉更贴近 Plex/Plexamp 原生桌面端的信息密度和交互层级；继续移除英文装饰 eyebrow、hero 式留白和夸张缩放，并进一步压缩无功能空白、重复说明和辅助标签。双主题、黑胶、渐变、阴影与 Cadilume 自有品牌保留，仍按 clean-room 实现。
4. macOS、Windows 和浏览器演示模式共享同一套 React 交互，但平台能力通过已有适配层分流。
5. Plex token、服务器地址、媒体路径和缓存键继续留在 Rust 边界；共享服务器继续服从 PMS ACL。
6. 每一阶段都先补针对性测试，再做 `pnpm check`、前端测试/构建、Rust 测试和实际最小窗口检查。

## 0. 统一视觉方向

### DS-001：贴近 Plex 原生桌面体验，定向去 AI 化

- 用户要求：Cadilume 改为更接近 Plex/Plexamp 原生桌面端的内容密度、信息层级和操作反馈，但不是把现有界面整体扁平化或重做成另一套风格。
- 双主题基线：深色与浅色是同等完整的两套主题表现，共享同一组语义 token、组件结构和交互状态；两者都要保持清楚的表面层级、可读对比和橙色强调，不将深色主题作为唯一视觉基准。
- 保留项：现有径向/线性渐变、玻璃模糊、渐变文字、光晕、阴影、圆角、胶囊按钮、黑胶与其他装饰效果全部保留；后续只能为双主题适配、对比度和一致性做必要校准，不能以“去 AI 化”为由统一删除。
- 第二轮修正：除英文装饰 eyebrow、hero 式大面积无效留白和夸张或弹跳式缩放外，继续删除不帮助决策的说明句、数量装饰和重复状态文案；缩短页面标题区、设置组和媒体详情的上下留白，把空间用于媒体内容和主要操作。不得借机删除功能信息、双主题或必要错误提示。
- 交互基线：hover/focus/active/disabled 必须可区分；允许不引发布局位移的轻微缩放、位移、颜色、透明度、边框、阴影和光晕变化，但禁止夸张放大或弹跳。过渡控制在 150–200ms，并遵守 `prefers-reduced-motion`。
- 覆盖范围：登录与启动 Loading、主壳和侧栏、资料库列表/卡片、详情页、设置、底栏播放器、展开播放器、右侧歌词、歌单弹窗及全局错误提醒。已实现的 UI 也需要按新方向复审，不能只调整后续新增页面。
- clean-room 边界：只参考 Plex/Plexamp 的信息密度、媒体优先级和交互层级；不复制其商标、品牌素材、字体、文案、图标、源码、内部标识或私有能力，Cadilume 名称、应用图标和语义 token 保持独立。
- 验收：在 `1280×820` 使用 Chrome 检查全部页面的深色/浅色矩阵；两套主题的信息层级、组件结构和状态完整一致；不存在英文装饰 eyebrow、hero 式无效留白、夸张缩放、重复说明和为凑版式保留的大块空白；现有渐变、光晕、阴影、圆角和黑胶语言在双主题下对比合格。
- 状态：首轮三项定向修饰已完成；用户复审认为密度和文案仍未达标，第二轮按 `$macos-design` 的原生桌面信息层级重新收口中。

## 1. 发布、登录与窗口生命周期

### PKG-001：DMG 构建后残留 `.app`

- 问题：`bundle/macos/Cadilume.app` 会被 Spotlight 或文件检索发现。
- 方案：DMG 只允许通过受控脚本构建；开始前清旧包，并在成功、失败及可捕获信号退出时精确删除 `Cadilume.app`。
- 验收：DMG 校验和包内签名通过；构建目录没有 `.app` 或同名符号链接。
- 状态：已实现，待整轮最终构建验证。

### AUTH-001：登录成功回调期间可重复点击

- 根因：旧按钮只在 `waiting` 禁用，认证成功后切换状态到页面重载之间存在可点击窗口。
- 方案：同步 in-flight 锁；等待浏览器和完成账号重载两个阶段都保持 spinner、`disabled` 与 `aria-busy`。
- 验收：快速双击只创建一次 PIN；回调完成前不能再次触发；失败后才恢复按钮。
- 状态：已实现并有 hook 测试。

### AUTH-002：界面暴露 PIN 登录字符串

- 方案：PIN 只作为浏览器认证参数，不进入 hook 返回值，不在按钮或提示文案中渲染。
- 验收：登录页 DOM 不包含 PIN。
- 状态：已实现。

### WIN-001：关闭到托盘后点击 Dock 无法恢复

- 根因：隐藏主窗口后没有处理 macOS `RunEvent::Reopen`。
- 方案：Dock 再激活时始终 show、unminimize、focus 主窗口，不能因桌面歌词等辅助窗口可见而跳过。
- 验收：关闭到菜单栏后点击 Dock 可恢复；显式退出仍真正结束进程。
- 状态：已实现，待真机回归。

### WIN-002：默认窗口尺寸

- 用户最终确认：恢复项目最初版本的默认窗口 `1280×820`，并将它同时设为最小尺寸，系统层面不允许继续缩小。历史审计确认初始提交 `e8dd783` 的默认值为 `1280×820`，后续 `8cdb54f` 才将默认值缩成 `960×640`。
- 验收：配置中的 width/minWidth 均为 `1280`，height/minHeight 均为 `820`；Chrome 在该尺寸无水平溢出；连接拓扑、播放器独立音量及右侧面板不会因响应式规则隐藏。
- 状态：已恢复并通过 Chrome 与 Tauri Release 编译验证。

## 2. 资料来源、账号与歌单

### SRC-001：服务器和音乐库不应常驻侧栏

- 方案：侧栏移除来源下拉框；服务器和 Music Section 只在设置页选择；来源腾出的侧栏空间用于常驻歌单区。
- 验收：侧栏没有来源选择器；设置页可选择、可显示连接类型，并提供“同步资料”；侧栏对应位置展示 LIST-002 定义的歌单区。
- 状态：来源迁移已实现并完成最小窗口检查；常驻歌单区待实现。

### SRC-002：设置入口与账号入口重复

- 方案：移除独立设置按钮和无功能的三点图标，只保留左下角账号卡，点击进入设置。
- 验收：侧栏底部只有一个账号入口，选中时状态明确。
- 状态：已实现。

### SRC-003：同步、退出入口整理

- 方案：右上角刷新迁入设置并命名“同步资料”；“退出账号”使用危险色；设置页删除“退出 Cadilume”，应用退出保留在原生菜单栏/托盘。
- 状态：已实现。

### SRC-004：连接拓扑在最小窗口不可见

- 根因：主栏已经根据 Plex resource 的 `local/relay` 标记生成“本地直连 / 远程直连 / Plex Relay”，但 `@media (max-width: 1120px)` 会直接隐藏 `.connection-pill`；旧最小窗口 `960×640` 因此始终看不到。
- 第二轮方案：连接拓扑作为关键运行状态常驻顶部，不再由响应式规则隐藏；本地直连、远程直连和 Relay 使用文字加状态点表达，不能只依赖颜色。恢复 `1280×820` 最小窗口后仍需验证标题、搜索和状态不会互相挤压。
- 边界：该标签说明当前选中服务器的发现/连接拓扑，不冒充逐曲真实直放/转码结果。逐曲实际媒体决策若要显示，仍需由 Rust 代理在上游成功后发布脱敏运行态事件。
- 验收：Chrome `1280×820` 深浅主题下均可直接看见完整标签；切换本地、远程和 Relay 演示状态时文字与可访问名称同步，页面无横向溢出。
- 状态：已实现常驻标签、文字/状态点和可访问名称；本地直连已完成 Chrome 实测，远程与 Relay 状态留在最终演示矩阵复验。

### LIST-001：当前账号所属歌单识别不全

- 用户要求：当前账号有权访问的普通音频歌单和智能音频歌单都必须出现，并且都能打开和播放；“能否播放”不能与“能否写入”混为同一个过滤条件。
- 当前冲突：现有实现固定请求 `smart=0`，前端又排除智能和只读条目，因此只能识别普通可写歌单，无法满足智能歌单展示与播放。
- 方案：使用所选服务器的账号级 per-server token 获取全部获授权的音频歌单，保留 `smart`、`readOnly` 等能力字段；普通、智能及只读音频歌单都进入展示/播放集合。添加歌曲时再使用独立的“可写目标”判断，只允许非智能且可写的普通歌单。
- 播放行为：智能歌单详情按 PMS 当前返回的动态曲目加载；单曲、播放全部、随机播放均以该次返回的曲目集合建立队列，不把智能歌单物化或改写成普通歌单。
- 验收：普通与智能音频歌单完整出现且均能打开、播放和随机播放；智能/只读歌单只从“添加到歌单”目标中排除；非音频与畸形条目不展示；共享服务器 ACL 失败不绕过。
- 状态：读取/写入能力分离、智能/只读歌单数据基础及 LIST-002 展示播放闭环均已完成。

### LIST-002：歌单常驻左侧侧栏

- 位置：在主导航下方、左下角账号卡上方增加常驻“歌单”区，使用原来源选择器腾出的空间；账号卡始终固定在侧栏底部，不随歌单滚动。
- 内容：普通歌单、智能歌单都显示；两类歌单使用一致的行布局，并通过图标加文案/辅助标签区分智能属性，不能只依赖颜色。点击歌单进入详情，当前歌单有明确选中态。
- 滚动：歌单列表自身使用 `min-height: 0` 与纵向滚动，不滚动品牌、主导航或账号卡；滚动条保持轻浅，建议 4–6px、透明轨道、低对比 thumb，hover/拖动时适度增强，并分别适配深色与浅色主题。
- 状态：加载中、空歌单、同步失败都只占用歌单区，不改变侧栏整体骨架；长名称单行省略并保留可访问名称。
- 验收：在 `960×640` 且歌单数量超过一屏时，只有歌单内部滚动，账号卡与导航坐标不变；滚动条可发现但不抢视觉；普通/智能歌单均可见，选中、hover、focus 状态在深浅主题下都清楚。
- 状态：已完成常驻侧栏、独立滚动、普通/智能/只读歌单详情及播放交互，并通过最小尺寸双主题实测。

## 3. 可读性与通用交互

### UI-001：全局字号过小

- 方案：现有 CSS 字号整体增加 2px；任何明确的像素字号下限为 12px，标题的 `clamp()` 两端同步增加。
- 第二轮纠正：资料库主导航与歌单行的主标签统一为 13px/相同字重和行高；恢复最初 `1280×820` 窗口后重新检查信息密度，不能用缩小字体为多余说明腾位置。
- 验收：主页、侧栏、设置、播放器和歌词窗口可见文本的 computed font size 不低于 12px；资料库与歌单主标签 computed 字号、字重一致。
- 状态：首轮已满足 12px 下限，第二轮统一侧栏层级并按恢复后的最小尺寸复验。

### UI-002：全局禁止文本选择

- 方案：主应用根节点全局设置 `user-select: none` 与 `-webkit-user-select: none`；仅对 `input`、`textarea`、`[contenteditable]` 和明确需要复制的诊断详情恢复 `user-select: text`，不使用 JavaScript 拦截选择事件。
- 验收：常规文本、卡片和播放器文案不可拖选；搜索框等编辑控件仍可放置光标、选择文字及使用复制/粘贴快捷键；键盘焦点不受影响。
- 状态：已完成纯 CSS 全局禁选与编辑/诊断例外，并通过深浅主题最小尺寸、输入选区和诊断详情实测。

### UI-003：循环/随机按钮选中态在 hover 时丢失

- 根因：hover 选择器优先级高于 active，已选中的主题色被白色覆盖。
- 方案：active + hover 保留主题色和主题背景；未选中 hover 才使用普通高亮。
- 状态：已实现，底栏和展开播放器均完成 computed-style 验证。

### UI-004：专辑/歌手卡片 hover 表达错误

- 要求：不显示悬浮播放图标；封面和头像常态带柔和阴影，hover 可使用受控的轻微缩放/位移、边框和主题色阴影，但不得出现夸张放大、弹跳或布局位移。
- 验收：专辑与歌手 hover 无播放三角图标、无布局跳动；深浅主题均有清晰但不过曝的阴影。
- 状态：已移除悬浮播放图标，完成专辑/歌手常态阴影及 hover/focus 主题阴影、边框和轻微位移，并通过深浅主题最小尺寸实测。

### UI-005：专辑直接随机播放

- 方案：专辑详情提供明确的“随机播放”动作，建立只包含该专辑曲目的队列并从随机曲目开始。
- 验收：点击后立即播放；队列不越出当前专辑；随机历史与上一首/下一首仍正确。
- 状态：已完成专辑上下文随机起播与队列边界验证。

### UI-006：启动 Loading 太小且画面空

- 方案：使用完整品牌加载卡、明确的恢复状态和背景层次，不再只显示小图标与小 spinner。
- 状态：已实现，待启动阶段截图回归，并纳入 DS-001 的三项定向修饰与深浅主题复审。

### UI-007：全局禁用右键菜单

- 方案：在应用根入口捕获 `contextmenu` 并阻止默认菜单，使资料库、卡片、播放器、歌词和设置都不再弹出 WebView 右键菜单；组件不得各自重复绑定。
- 编辑边界：禁用右键不等于禁用键盘编辑。输入框仍保留光标、选择、复制、粘贴及 macOS 标准快捷键；诊断详情仍可通过已有复制路径使用。
- 验收：Chrome 对根页面、媒体卡片、歌词与播放器派发可取消的 `contextmenu` 事件时均被阻止；搜索框键盘输入、选择和复制仍正常。
- 状态：已在应用入口全局实现并增加处理器单元测试；Chrome 实际右键与输入框 `⌘A` 选择通过。

### UI-008：压缩设置与内容页冗余说明

- 方案：设置组仅保留能区分选项或解释安全边界的必要文字，删除“明亮、柔和”“适合夜间”等显然描述和重复的账号/菜单栏说明；资料库、歌单和详情页删除数量装饰、重复副标题及大块标题留白。危险操作、转码边界和失败处理仍保留必要信息。
- 视觉：设置回归 macOS 偏好设置式紧凑分组，单行标签与控件优先，不做网页营销卡片；页面内容从标题后立即开始，保持 8px 网格与 12–16px 内容间距。
- 验收：Chrome `1280×820` 下设置、资料库、歌单详情首屏有效内容明显增加；没有无功能大空白，控件含义仍可从标签和状态独立理解。
- 状态：待实现。

## 4. 播放器、AirPlay 与错误反馈

### PLAY-001：macOS AirPlay 需要二次点击

- 根因：底栏按钮先打开播放设备侧栏，侧栏里才调用 WebKit 系统选择器。
- 首轮方案：macOS 底栏 AirPlay 按钮直接调用当前 Audio 的 `webkitShowPlaybackTargetPicker()`；Windows/其他平台继续使用设备面板。
- 第二轮反馈：系统面板仍有卡顿和 `Show More` 二段展开，体验不自然。先确认这是 WebKit 系统 picker 的公共 API 行为还是 Cadilume 自定义面板造成；若 WebKit picker 本身受限，评估只用公开 `AVRoutePickerView` 的原生桥接，不使用私有 API、模拟点击或自绘虚假设备列表。
- 验收：一次点击只出现一个系统路由选择界面，不先打开 Cadilume 侧栏、不重复触发；展开层和普通底栏行为一致。系统自身无法由应用控制的分组/更多项目需在记录中明确，不以不可靠 DOM 技巧规避。
- 状态：首轮单击直达已完成；第二轮公共 API 与卡顿根因待真机复验。

### PLAY-002：底栏进度条和音量条看不出当前值

- 方案：根据当前进度/音量写入 CSS 进度变量，用主题色绘制已完成区，轨道色绘制剩余区；静音时音量填充为 0。
- 验收：0%、中间值、100% 和静音状态都可直接辨认，深浅主题对比足够。
- 状态：已完成底栏进度/音量 CSS 填充、WebKit/Firefox 轨道适配和静音归零，并通过深浅主题最小尺寸实测。

### PLAY-003：播放按钮配色、hover 与光学居中

- 方案：底栏主播放键使用主题色、清晰 hover/focus/disabled 状态；播放三角形做 1px 光学校正，暂停图标保持几何居中。

### PLAY-004：播放失败提示错误且过小

- 现象：底栏显示被截断的 `MediaError code 4 ... 当前音源已经是 320 kbps` 调试串，用户不容易发现，也不知道如何处理。
- 方案：播放失败进入覆盖播放器与内容区的全局提醒；首行给出可理解结论和可行动入口，不在底栏放小字；原始技术原因只进入可展开诊断或日志。
- 验收：任何播放失败都通过 `role="alert"`/live region 出现全局提醒；主提醒不展示 `MediaError code 4`、被截断的调试串或“已是 320 kbps”这类内部推断；提供重试或前往设置等有效动作；关闭后不影响控制，同类错误可再次出现。
- 状态：已完成全局提醒、可靠重试、设置定位与深浅主题最小尺寸实测。

### PLAY-005：320 kbps 兼容源仍无法播放

- 分析方向：区分 PMS 转码响应错误、错误 MIME/Range、票据失效和 WebView codec 拒绝；检查失败重试是否错误地把“已是 320 kbps”当成终点。
- 验收：有可用连接/兼容转码时自动恢复；最终失败时全局提醒包含可行动建议，日志保留技术原因。
- 状态：有界兼容码率回退、全量自动验证与内部浏览器最小尺寸实测已完成；此前真实失败曲目仍需在用户实际 PMS 上端到端复播，完成前不宣称所有曲目均已验证解决。

### PLAY-006：评估可复用播放内核，不自行重造解码器

- 用户方向：优先寻找维护中的现成播放模块，不复制 Plexamp 私有实现，也不自行重造完整解码、输出和歌词时钟；若现成模块仍只是包装浏览器 `<audio>`，必须明确它无法解决当前 WebView 时钟与可听声音可能不一致的问题。
- Plexamp 边界：本机 Plexamp 4.13.2 的桌面音频由私有 `treble.node` 和 BASS 动态库承担；ASAR 将 `treble` 声明为内部 `file:player` 依赖，没有可安装的公开包。BASS 也不是可直接按 Cadilume 当前 MIT 边界复制分发的开源内核，因此该组合只能做 clean-room 行为对照，不能复用二进制或源码。
- React 一体化播放器结论：`twist-aplayer`、`react-jinke-music-player`、`lrc-audio-player` 等虽然提供播放器和 LRC 接口，底层仍是 `HTMLAudioElement.currentTime`。其中 `twist-aplayer` 还把进度取整到秒并按固定 16px 行高移动歌词；`lrc-audio-player` 的可选 `ffmpeg.wasm` CBR 转换会在客户端转码，违反 Cadilume“转换只交给 PMS”的既定边界。这些方案不能作为当前播放可靠性或歌词对时修复。
- 独立播放内核候选：`libmpv` 是可嵌入的成熟开源媒体内核，支持多格式、外部字幕和时间/延迟控制，但它是原生后端而非 React 插件，也不提供 Plexamp 式右侧歌词组件；默认 GPL 构建与可选 LGPL 构建、macOS/Windows 二进制打包、AirPlay、系统媒体会话、独立音量、签名和 DMG 体积均需单独验证。若后续考虑，必须先做隔离原型和许可证审查，不能直接替换当前播放器。
- 决策门槛：先完成 LYR-002 同曲真机采样，确认偏快来自歌词数据还是播放时钟；只有证据指向 WebView 播放时钟/输出链路且无法在现有架构内可靠校正时，才启动播放器内核替换 RFC。RFC 必须比较原始直放、PMS 转码、预缓冲切换、AirPlay、后台播放、包体和跨平台维护成本。
- 状态：只读评估已归档，尚未选择或接入任何第三方播放模块，未安装依赖、未修改播放代码。

### LYR-004：对照 Plexamp 歌词链路并评估 React 歌词组件

- Plexamp 4.13.2 结构：桌面端为 Electron + React Native Web + MobX；歌词前端与私有 Treble/BASS 播放内核分离，不存在“播放模块自动附带完整歌词 UI”。歌词流优先级为首个本地歌词 > 首个 timed 歌词 > 首个歌词流。
- 数据与时间：Plexamp 不在前端解析原始 LRC/SRT/VTT，而是请求 PMS/provider 已规范化的 `MediaContainer.Lyrics.Line[]`，直接读取毫秒 `startOffset/endOffset` 和首个 `Span.text`。Treble 状态时间由秒转换成毫秒后与歌词区间比较，没有发现固定提前/延后补偿；当前行使用二分查找，点击歌词跳到 `startOffset + 50ms`。
- 滚动：Plexamp 使用 React Native `FlatList`；歌词组件挂载约 1 秒后监听活动行，调用 `scrollToIndex({ index, viewPosition: 0.5 })` 把当前行放到列表中部。它没有自定义行切换渐变。Cadilume 当前“独立歌词容器 + 当前行居中”的滚动方向与其一致，因此滚动动画不是歌词偏快的主要嫌疑。
- 关键差异：Cadilume 用活动 `HTMLAudioElement.currentTime` 驱动歌词；Plexamp 用私有原生播放内核上报的 `player.time`，并以整秒 ticker 补时。Treble 是否进一步补偿声卡、AirPlay 或其他输出延迟无法从发布包 JavaScript 层确定；目前只能把播放时钟语义差异列为高优先级嫌疑，不能当成已证实根因。
- React 歌词组件评估：`react-lrc`（MIT）支持 LRC、当前行与用户滚动后恢复自动滚动，但仍要求外部传入 `currentMillisecond`，居中公式与 Cadilume 现有实现基本相同，且不能直接保留 PMS `endOffset`/多格式数据；`@applemusic-like-lyrics/react` 功能更完整，但为 AGPL-3.0-only、依赖较重且项目自身提示不宜直接用于生产。两者都不会修正错误的播放时钟。
- 实施原则：不为了“用了插件”而替换现有歌词组件。先按 LYR-002 用同一真实曲目和同一歌词源采集开头/中段/结尾的 PMS 原始 offset、Cadilume 播放时钟、实际唱词起点与 Plexamp 对照；随后再决定是修数据源、引入明确可验证的 delay，还是更换播放时钟/内核。
- 状态：Plexamp 发布包与 React 插件只读审计已完成；本项仅进入计划，未安装歌词依赖、未修改歌词解析、时钟或滚动代码。

### LYR-005：以 Chrome 中 Plex Web 同曲行为作为公开实现对照

- 目标：使用用户已登录并已打开的 Chrome Plex Web 页面，对同一 metadata key、同一歌词流和同一播放输出进行对照；不读取 cookie、localStorage、密码或 token，不复制 Plex Web 源码或私有资源。

### NP-001：切歌后展开播放器整体上移，看起来像两套 UI

- 截图结论：不是两套组件。两张 `2560×1576` 截图中的 header、唱片、歌词栏、进度条和控制器属于同一个 `NowPlayingView`，第二张相对第一张是整层统一平移约 54 个物理像素，而不是局部内容重排。
- 根因：当前歌词变化时对激活歌词调用 `scrollIntoView({ block: "center" })`。该 API 会滚动所有可滚动祖先；外层播放器虽然使用 `overflow: hidden`，仍可被程序化改变滚动位置，因此歌词进入中段后连整个播放器外层一起滚动，开头又回到顶部，看起来像切换了另一套 UI。歌词行数或标题高度不是本次整体平移的根因。
- 方案：为歌词列表保存独立 ref，只在该列表内计算目标位置并调用 `scrollTo`；外层改为不可滚动的 `overflow: clip`；切歌时重置歌词列表自身的 `scrollTop`；header/content/controller 继续保持固定三段骨架。
- 验收：在 `960×640` 以及截图对应尺寸连续切换短/长标题、无歌词/55 行/89 行歌词、`0:00`/播放中状态，关闭键、唱片中心、进度条和控制按钮的 `DOMRect` 坐标漂移不超过 1–2 CSS px；只有歌词列表内部滚动，外层 `scrollTop` 始终为 0。
- 状态：已完成独立歌词滚动、切歌复位和固定三段骨架，并通过最小尺寸实测。

### 2026-07-29 — PLAY-005：播放兼容回退

- 根因：旧逻辑只允许 `auto/original → 320` 一次回退；远程 `auto` 已解析为 320 时会直接终止，显式 320/256 也没有继续向下兼容的路径；`audio.play()` rejection 与 `MediaError` 事件还可能竞态覆盖正在执行的回退。
- 实现：改为有界状态机；`auto/original` 按需尝试 `320 → 256 → 192`，已识别为 320 的自动源直接从 256 开始，显式质量只向更低档降级；pending 状态防止重复请求，获取 URL 失败也只消费当前档位一次，旧异步请求不能覆盖新回退。
- Relay 边界：本机票据安全公开 320/256/192 的实际转码标记，前端将该标记作为回退上限；`auto + Relay` 已是 192 时终止而不会反向升级到 320，标记错配和未知查询仍会被本机代理拒绝。
- 错误结构：保留回退过程兼容状态，同时新增终止态 `playbackFailure`，分离用户结果与脱敏技术诊断，供 PLAY-004 全局提醒消费。
