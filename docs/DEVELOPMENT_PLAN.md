# Cadilume 当前开发清单与验收计划

更新日期：2026-07-29。

本文集中记录本轮用户反馈、根因分析、实现边界和验收顺序。代码调整应逐项对应本文，不以临时样式或固定延迟掩盖播放、歌词或布局问题。

当前状态：2026-07-29 已恢复开发。每完成一个独立步骤，必须先更新本文记录实现与验证结果，再使用 Codex 内部浏览器按应用最小尺寸 `960×640` 完成 Web UI 实测，确认通过后才进入下一步。

## 执行原则

1. 先保证能登录、能恢复窗口、能稳定播放，并让失败信息明确可见。
2. 播放器骨架、底栏和歌词容器必须保持稳定；曲目、封面或歌词变化不得推动整套 UI 上下跳动。
3. 整体视觉更贴近 Plex/Plexamp 原生桌面端的信息密度和交互层级；去 AI 化只移除英文装饰 eyebrow、hero 式留白和夸张缩放，其余现有视觉效果保留，并继续使用 Cadilume 自有品牌和 clean-room 实现。
4. macOS、Windows 和浏览器演示模式共享同一套 React 交互，但平台能力通过已有适配层分流。
5. Plex token、服务器地址、媒体路径和缓存键继续留在 Rust 边界；共享服务器继续服从 PMS ACL。
6. 每一阶段都先补针对性测试，再做 `pnpm check`、前端测试/构建、Rust 测试和实际最小窗口检查。

## 0. 统一视觉方向

### DS-001：贴近 Plex 原生桌面体验，定向去 AI 化

- 用户要求：Cadilume 改为更接近 Plex/Plexamp 原生桌面端的内容密度、信息层级和操作反馈，但不是把现有界面整体扁平化或重做成另一套风格。
- 双主题基线：深色与浅色是同等完整的两套主题表现，共享同一组语义 token、组件结构和交互状态；两者都要保持清楚的表面层级、可读对比和橙色强调，不将深色主题作为唯一视觉基准。
- 保留项：现有径向/线性渐变、玻璃模糊、渐变文字、光晕、阴影、圆角、胶囊按钮、黑胶与其他装饰效果全部保留；后续只能为双主题适配、对比度和一致性做必要校准，不能以“去 AI 化”为由统一删除。
- 仅删除三项：英文装饰 eyebrow、hero 式大面积无效留白、夸张或弹跳式缩放。页面标题改用直接、清楚的中文层级；空间用于媒体内容和主要操作。
- 交互基线：hover/focus/active/disabled 必须可区分；允许不引发布局位移的轻微缩放、位移、颜色、透明度、边框、阴影和光晕变化，但禁止夸张放大或弹跳。过渡控制在 150–200ms，并遵守 `prefers-reduced-motion`。
- 覆盖范围：登录与启动 Loading、主壳和侧栏、资料库列表/卡片、详情页、设置、底栏播放器、展开播放器、右侧歌词、歌单弹窗及全局错误提醒。已实现的 UI 也需要按新方向复审，不能只调整后续新增页面。
- clean-room 边界：只参考 Plex/Plexamp 的信息密度、媒体优先级和交互层级；不复制其商标、品牌素材、字体、文案、图标、源码、内部标识或私有能力，Cadilume 名称、应用图标和语义 token 保持独立。
- 验收：在 `960×640` 建立覆盖范围内全部页面的深色/浅色截图矩阵；两套主题的信息层级、组件结构和状态完整一致；界面不存在英文装饰 eyebrow、hero 式无效留白或夸张缩放；现有渐变、玻璃、光晕、阴影、圆角和胶囊语言仍然可见且在双主题下对比合格。
- 状态：已归档，待需求收齐后统一设计与实现。

## 1. 发布、登录与窗口生命周期

### PKG-001：DMG 构建后残留 `.app`

- 问题：`bundle/macos/Cadilume.app` 会被 Spotlight 或文件检索发现。
- 方案：DMG 只允许通过受控脚本构建；开始前清旧包，并在成功、失败及可捕获信号退出时精确删除 `Cadilume.app`。
- 验收：DMG 校验和包内签名通过；构建目录没有 `.app` 或同名符号链接。
- 状态：已实现，待整轮最终构建验证。

### AUTH-001：登录成功回调期间可重复点击

- 根因：旧按钮只在 `waiting` 禁用，认证成功后切换状态到页面重载之间存在可点击窗口。
- 方案：同步 in-flight 锁；等待浏览器和完成账号重载两个阶段都保持 spinner、`disabled` 与 `aria-busy`。
- 验收：快速双击只创建一次 PIN；回调完成前不能再次触发；失败后才恢复按钮。
- 状态：已实现并有 hook 测试。

### AUTH-002：界面暴露 PIN 登录字符串

- 方案：PIN 只作为浏览器认证参数，不进入 hook 返回值，不在按钮或提示文案中渲染。
- 验收：登录页 DOM 不包含 PIN。
- 状态：已实现。

### WIN-001：关闭到托盘后点击 Dock 无法恢复

- 根因：隐藏主窗口后没有处理 macOS `RunEvent::Reopen`。
- 方案：Dock 再激活时始终 show、unminimize、focus 主窗口，不能因桌面歌词等辅助窗口可见而跳过。
- 验收：关闭到菜单栏后点击 Dock 可恢复；显式退出仍真正结束进程。
- 状态：已实现，待真机回归。

### WIN-002：默认窗口尺寸

- 要求：默认尺寸就是最小尺寸 `960×640`，不可继续缩小。
- 验收：配置中的 width/height/minWidth/minHeight 全部为 `960/640`，该尺寸无水平溢出。
- 状态：已实现并完成浏览器尺寸检查。

## 2. 资料来源、账号与歌单

### SRC-001：服务器和音乐库不应常驻侧栏

- 方案：侧栏移除来源下拉框；服务器和 Music Section 只在设置页选择；来源腾出的侧栏空间用于常驻歌单区。
- 验收：侧栏没有来源选择器；设置页可选择、可显示连接类型，并提供“同步资料”；侧栏对应位置展示 LIST-002 定义的歌单区。
- 状态：来源迁移已实现并完成最小窗口检查；常驻歌单区待实现。

### SRC-002：设置入口与账号入口重复

- 方案：移除独立设置按钮和无功能的三点图标，只保留左下角账号卡，点击进入设置。
- 验收：侧栏底部只有一个账号入口，选中时状态明确。
- 状态：已实现。

### SRC-003：同步、退出入口整理

- 方案：右上角刷新迁入设置并命名“同步资料”；“退出账号”使用危险色；设置页删除“退出 Cadilume”，应用退出保留在原生菜单栏/托盘。
- 状态：已实现。

### LIST-001：当前账号所属歌单识别不全

- 用户要求：当前账号有权访问的普通音频歌单和智能音频歌单都必须出现，并且都能打开和播放；“能否播放”不能与“能否写入”混为同一个过滤条件。
- 当前冲突：现有实现固定请求 `smart=0`，前端又排除智能和只读条目，因此只能识别普通可写歌单，无法满足智能歌单展示与播放。
- 方案：使用所选服务器的账号级 per-server token 获取全部获授权的音频歌单，保留 `smart`、`readOnly` 等能力字段；普通、智能及只读音频歌单都进入展示/播放集合。添加歌曲时再使用独立的“可写目标”判断，只允许非智能且可写的普通歌单。
- 播放行为：智能歌单详情按 PMS 当前返回的动态曲目加载；单曲、播放全部、随机播放均以该次返回的曲目集合建立队列，不把智能歌单物化或改写成普通歌单。
- 验收：普通与智能音频歌单完整出现且均能打开、播放和随机播放；智能/只读歌单只从“添加到歌单”目标中排除；非音频与畸形条目不展示；共享服务器 ACL 失败不绕过。
- 状态：普通可写歌单识别已实现并有测试；智能/只读歌单的展示与播放待补充。

### LIST-002：歌单常驻左侧侧栏

- 位置：在主导航下方、左下角账号卡上方增加常驻“歌单”区，使用原来源选择器腾出的空间；账号卡始终固定在侧栏底部，不随歌单滚动。
- 内容：普通歌单、智能歌单都显示；两类歌单使用一致的行布局，并通过图标加文案/辅助标签区分智能属性，不能只依赖颜色。点击歌单进入详情，当前歌单有明确选中态。
- 滚动：歌单列表自身使用 `min-height: 0` 与纵向滚动，不滚动品牌、主导航或账号卡；滚动条保持轻浅，建议 4–6px、透明轨道、低对比 thumb，hover/拖动时适度增强，并分别适配深色与浅色主题。
- 状态：加载中、空歌单、同步失败都只占用歌单区，不改变侧栏整体骨架；长名称单行省略并保留可访问名称。
- 验收：在 `960×640` 且歌单数量超过一屏时，只有歌单内部滚动，账号卡与导航坐标不变；滚动条可发现但不抢视觉；普通/智能歌单均可见，选中、hover、focus 状态在深浅主题下都清楚。
- 状态：待实现。

## 3. 可读性与通用交互

### UI-001：全局字号过小

- 方案：现有 CSS 字号整体增加 2px；任何明确的像素字号下限为 12px，标题的 `clamp()` 两端同步增加。
- 验收：主页、设置、播放器和歌词窗口可见文本的 computed font size 不低于 12px。
- 状态：已实现并在 `960×640` 视口验证。

### UI-002：全局禁止文本选择

- 方案：主应用根节点全局设置 `user-select: none` 与 `-webkit-user-select: none`；仅对 `input`、`textarea`、`[contenteditable]` 和明确需要复制的诊断详情恢复 `user-select: text`，不使用 JavaScript 拦截选择事件。
- 验收：常规文本、卡片和播放器文案不可拖选；搜索框等编辑控件仍可放置光标、选择文字及使用复制/粘贴快捷键；键盘焦点不受影响。
- 状态：待实现。

### UI-003：循环/随机按钮选中态在 hover 时丢失

- 根因：hover 选择器优先级高于 active，已选中的主题色被白色覆盖。
- 方案：active + hover 保留主题色和主题背景；未选中 hover 才使用普通高亮。
- 状态：已实现，底栏和展开播放器均完成 computed-style 验证。

### UI-004：专辑/歌手卡片 hover 表达错误

- 要求：不显示悬浮播放图标；封面和头像常态带柔和阴影，hover 可使用受控的轻微缩放/位移、边框和主题色阴影，但不得出现夸张放大、弹跳或布局位移。
- 验收：专辑与歌手 hover 无播放三角图标、无布局跳动；深浅主题均有清晰但不过曝的阴影。
- 状态：待实现。

### UI-005：专辑直接随机播放

- 方案：专辑详情提供明确的“随机播放”动作，建立只包含该专辑曲目的队列并从随机曲目开始。
- 验收：点击后立即播放；队列不越出当前专辑；随机历史与上一首/下一首仍正确。
- 状态：待实现。

### UI-006：启动 Loading 太小且画面空

- 方案：使用完整品牌加载卡、明确的恢复状态和背景层次，不再只显示小图标与小 spinner。
- 状态：已实现，待启动阶段截图回归，并纳入 DS-001 的三项定向修饰与深浅主题复审。

## 4. 播放器、AirPlay 与错误反馈

### PLAY-001：macOS AirPlay 需要二次点击

- 根因：底栏按钮先打开播放设备侧栏，侧栏里才调用 WebKit 系统选择器。
- 方案：macOS 底栏 AirPlay 按钮直接调用当前 Audio 的 `webkitShowPlaybackTargetPicker()`；Windows/其他平台继续使用设备面板。
- 状态：待实现。

### PLAY-002：底栏进度条和音量条看不出当前值

- 方案：根据当前进度/音量写入 CSS 进度变量，用主题色绘制已完成区，轨道色绘制剩余区；静音时音量填充为 0。
- 验收：0%、中间值、100% 和静音状态都可直接辨认，深浅主题对比足够。
- 状态：待实现。

### PLAY-003：播放按钮配色、hover 与光学居中

- 方案：底栏主播放键使用主题色、清晰 hover/focus/disabled 状态；播放三角形做 1px 光学校正，暂停图标保持几何居中。
- 状态：待实现。

### PLAY-004：播放失败提示错误且过小

- 现象：底栏显示被截断的 `MediaError code 4 ... 当前音源已经是 320 kbps` 调试串，用户不容易发现，也不知道如何处理。
- 方案：播放失败进入覆盖播放器与内容区的全局提醒；首行给出可理解结论和可行动入口，不在底栏放小字；原始技术原因只进入可展开诊断或日志。
- 验收：任何播放失败都通过 `role="alert"`/live region 出现全局提醒；主提醒不展示 `MediaError code 4`、被截断的调试串或“已是 320 kbps”这类内部推断；提供重试或前往设置等有效动作；关闭后不影响控制，同类错误可再次出现。
- 状态：待实现。

### PLAY-005：320 kbps 兼容源仍无法播放

- 分析方向：区分 PMS 转码响应错误、错误 MIME/Range、票据失效和 WebView codec 拒绝；检查失败重试是否错误地把“已是 320 kbps”当成终点。
- 验收：有可用连接/兼容转码时自动恢复；最终失败时全局提醒包含可行动建议，日志保留技术原因。
- 状态：已完成有界兼容码率回退、全量自动验证与内部浏览器最小尺寸实测。

## 5. 歌词与展开播放器

### LYR-001：移除浮动桌面歌词，恢复右侧歌词栏

- 方案：底栏歌词按钮打开/关闭主窗口右侧歌词栏；移除 always-on-top 桌面歌词入口、窗口、事件同步和托盘菜单项。
- 验收：主窗口右侧可查看、滚动、点击跳转歌词；应用不再创建或控制桌面歌词窗口。
- 状态：待实现。

### LYR-002：歌词相对真实播放进度偏快

- 分析方向：核对 Plex timed lyric 原始单位、LRC/SRT/VTT 解析、Audio `currentTime`、用户 delay 的正负方向，以及切换预缓冲 Audio 后的时钟来源；以同曲 Plexamp 表现作为真机对照。
- 原则：先修时间基准或符号错误，不直接加入未经验证的固定延迟。
- 验收：至少用同一首 timed lyric 曲目在开头、中段、结尾对照，当前行不持续领先声音。
- 状态：待定位并补解析/时钟测试。

### LYR-003：歌词行切换生硬

- 方案：当前行使用颜色/透明度/轻微位移渐变；滚动保持平滑并尊重 `prefers-reduced-motion`，不使用会推动布局的尺寸动画。
- 状态：待实现。

### NP-001：切歌后展开播放器整体上移，看起来像两套 UI

- 截图结论：不是两套组件。两张 `2560×1576` 截图中的 header、唱片、歌词栏、进度条和控制器属于同一个 `NowPlayingView`，第二张相对第一张是整层统一平移约 54 个物理像素，而不是局部内容重排。
- 根因：当前歌词变化时对激活歌词调用 `scrollIntoView({ block: "center" })`。该 API 会滚动所有可滚动祖先；外层播放器虽然使用 `overflow: hidden`，仍可被程序化改变滚动位置，因此歌词进入中段后连整个播放器外层一起滚动，开头又回到顶部，看起来像切换了另一套 UI。歌词行数或标题高度不是本次整体平移的根因。
- 方案：为歌词列表保存独立 ref，只在该列表内计算目标位置并调用 `scrollTo`；外层改为不可滚动的 `overflow: clip`；切歌时重置歌词列表自身的 `scrollTop`；header/content/controller 继续保持固定三段骨架。
- 验收：在 `960×640` 以及截图对应尺寸连续切换短/长标题、无歌词/55 行/89 行歌词、`0:00`/播放中状态，关闭键、唱片中心、进度条和控制按钮的 `DOMRect` 坐标漂移不超过 1–2 CSS px；只有歌词列表内部滚动，外层 `scrollTop` 始终为 0。
- 状态：原因已定位并归档，待后续实现。

### 2026-07-29 — PLAY-005：播放兼容回退

- 根因：旧逻辑只允许 `auto/original → 320` 一次回退；远程 `auto` 已解析为 320 时会直接终止，显式 320/256 也没有继续向下兼容的路径；`audio.play()` rejection 与 `MediaError` 事件还可能竞态覆盖正在执行的回退。
- 实现：改为有界状态机；`auto/original` 按需尝试 `320 → 256 → 192`，已识别为 320 的自动源直接从 256 开始，显式质量只向更低档降级；pending 状态防止重复请求，获取 URL 失败也只消费当前档位一次，旧异步请求不能覆盖新回退。
- Relay 边界：本机票据安全公开 320/256/192 的实际转码标记，前端将该标记作为回退上限；`auto + Relay` 已是 192 时终止而不会反向升级到 320，标记错配和未知查询仍会被本机代理拒绝。
- 错误结构：保留回退过程兼容状态，同时新增终止态 `playbackFailure`，分离用户结果与脱敏技术诊断，供 PLAY-004 全局提醒消费。
- 自动验证：`pnpm check` 通过；`pnpm test` 7 个文件、65 项测试通过；`pnpm build` 通过；Rust 35 项测试通过；`cargo fmt --check` 与 `git diff --check` 通过。
- Web UI：Codex 内部浏览器新建干净标签页并固定 `960×640`；通过可见设置关闭预缓冲后进入歌曲页播放，正在播放信息与控制完整，底栏 `DOMRect.bottom=640`、宽度 960；页面无横向溢出，可见文字最小 12px，控制台 warning/error 为 0。
- 实测边界：内部浏览器使用演示播放分支，不创建 Tauri 本机音频代理；真实码率回退顺序和终止边界由 32 项 `usePlayer` 定向测试与 17 项 `stream_proxy` 定向测试覆盖，浏览器负责验证播放态 UI、最小尺寸和运行稳定性。
- 结论：PLAY-005 通过，可以进入 PLAY-004 全局播放失败提醒。
