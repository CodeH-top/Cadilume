# Cadilume、Plexamp 与网易云音乐缓存机制对比（2026-08-09）

> 部分只记录本机已安装版本产生的缓存文件、稀疏块占用和明文索引，不反编译应用，不读取

## 最终结论

Cadilume 已采用“**固定 1 GiB + 稀疏分段缓存 v2**”。它是播放产生的临时流式缓存，
不是离线下载：当前曲目先取 256 KiB 头部，随后仅在解码或 seek 遇到缺口时取目标所在的
对齐 2 MiB Range；开启预缓冲时，只为 Rust 队列确认的真实下一首建立第二 read head，
约 4 秒 PCM 就绪即可挂入 rodio，不要求整首下载完成。

容量按 `media.sparse` 与 `index.json` 的**实际分配磁盘块**计算，而不是稀疏文件的逻辑
长度；硬上限固定 1 GiB，同时要求写入后仍保留至少 1 GiB 系统可用空间。LRU 保护当前与
真实下一首，其他最旧条目先淘汰；没有空间就拒绝新块，不突破预算。代码没有资料库扫描、
整条队列下载或“下下首”预取路径，因此不会把整个音乐库悄悄复制到本地。

PMS 不支持 Range 时，只有当前曲目为保证兼容播放才退回连续读取；下一首遇到 `200` 会
直接放弃预缓冲，绝不升级为完整下载。这个边界是 v2 防止后台吞入大文件的关键结论。

## 本机网易云音乐观察

本机安装的是网易云音乐 macOS `3.1.10`（Bundle ID `com.netease.163music`）。在线播放
缓存位于：

```text
~/Library/Application Support/com.netease.163music/Caches/online_play_cache
```

每个媒体身份对应三类文件：

| 文件 | 本机可观察作用 |
| --- | --- |
| `.uc!` | 具有完整媒体逻辑长度的稀疏文件，只有已缓存区间实际占用磁盘块 |
| `.idx!` | 明文 JSON，包含媒体逻辑 `size` 和已缓存连续区间 `zone` |
| `.info` | 独立、不透明的元数据；本轮不解码其内容 |

现场三个 `.uc!` 的逻辑大小合计 `123,528,193` 字节，连同索引/元数据后的文件逻辑大小为
`123,531,957` 字节；`du` 实际占用约 `65.6 MiB`。对应 `.idx!` 中两首只保存了开头区间，
另一首区间覆盖完整文件。这说明它能保留逻辑地址空间和区间索引，而不要求先写满整首。

这套模型适合按需 Range、快速 seek 和断点续传，也能减少跳歌后的浪费；代价是播放器必须
知道哪些区间存在、遇到缺口如何发起请求、多个 read head 如何协调、何时校验已写区间。
Cadilume v2 已以自己的 `SegmentReader`、合并区间索引和稀疏文件完成这些能力；它只借鉴
可观察的行为原则，不复制网易云的文件格式、私有协议或实现。

## 为什么 14 个音频会占 491 MB

旧 v1 在“原始质量”下保存 PMS 返回的完整源文件；FLAC、ALAC 或高规格无损曲目单首几十
MiB 很常见。`491 / 14` 约为每首 `35 MiB`，与 14 个完整无损文件的量级一致，不是整库下载
的证据，但确实说明“完整文件渐进缓存”对只听一部分或频繁跳歌的场景浪费明显。

v2 不迁移这些旧完整文件，启动时会删除旧 `native-audio/downloads`。新缓存只保留实际被
解码、探测或 seek 读取的区间；如果一首歌从头到尾完整播放，它最终仍可能缓存整首，这是
正常的重播优化，但没有听到的其他歌曲不会因此下载。真实下一首最多只产生满足有界 PCM
准备所需的少量区间，不再提前占用完整曲目大小。

## Cadilume 当前预算模型

| 维度 | 本轮实现 |
| --- | --- |
| 容量 | 固定 1 GiB；不持久化用户容量选项，设置页只显示固定上限 |
| 主动范围 | 当前曲目；开启预缓冲时再为真实下一首建立第二 read head；无下下首、整队列或曲库扫描 |
| 请求粒度 | 首段 256 KiB；后续缺口与 seek 使用对齐 2 MiB Range |
| 无 Range 回退 | 当前曲目允许连续兼容读取；下一首拒绝完整 fallback |
| 占用统计 | `media.sparse` 与 `index.json` 的实际分配块；逻辑长度和空洞不计作已缓存媒体 |
| 准入 | 写每个已验证区间前复核固定预算与 1 GiB 低磁盘保留；不足即拒绝 |
| LRU | 整条目淘汰最旧 `index.json` mtime，保护所有当前/下一首活动条目 |
| 完整性 | 校验 `206 Content-Range`、响应体长度、ETag/Last-Modified、总长度与 `416` |
| 启动恢复 | 删除临时索引、截断文件和不可续传的无 Range 半成品；显式打孔未提交区间 |
| 清理 | 停止 Rust 播放和下载，清空前端/Rust 队列与持久化会话，再删除封面和音频缓存 |
| 设置展示 | 封面缓存一行、音频缓存一行；音频显示实际占盘 / 1 GiB、完整与部分缓存数量 |

容量准入按下列顺序执行：

```text
解码/seek 请求位置
  -> index.json 命中已提交区间：直接读取稀疏文件
  -> 缺口：当前曲目优先取得网络许可
  -> 校验 Range 响应与媒体版本
  -> 统计实际分配块 + 本次响应体，并检查低磁盘保留
  -> 超额则按 LRU 淘汰未活动条目；仍不足则拒绝写入
  -> 写入目标 offset、sync，再原子提交新区间索引
```

Range 响应先完整放在最多 2 MiB 的内存缓冲中，只有字节数与声明区间一致才写盘；索引在
数据 `sync` 后原子替换，因此崩溃不会把未提交空洞误认为可播放数据。同一缓存身份并发打开
时共享同一运行状态与 fetch 锁，避免当前/下一首重复写同一稀疏文件。

## 后续优化边界

v2 已解决本轮最重要的完整文件浪费。后续优化应以遥测之外的本地可见指标和真实弱网验收为
依据，例如 Range 合并命中率、首播耗时、seek 请求量和 LRU 抖动；不得为了提高命中率恢复
整队列预取，凭据、URL 和媒体身份也不得进入日志。

离线下载继续保持独立：由用户显式选择项目、展示预计大小和进度、允许暂停/删除，并采用
自己的容量与保留规则；不能把临时分段缓存悄悄提升为离线资料库或整库副本。
