# Cadilume、Plexamp 与网易云音乐缓存机制对比（2026-08-08）

> 部分只记录本机已安装版本产生的缓存文件、稀疏块占用和明文索引，不反编译应用，不读取

## 最终结论

Cadilume 本轮采用“**有界流式缓存**”，不是“离线下载”：默认 1 GiB，可选 1–10 GiB；
当前曲目渐进下载，开启预缓冲时只额外完整缓存 Rust 队列确认的真实下一首；完整文件和
下载中的 `.part` 共同占用同一预算，最旧完整文件按 LRU 淘汰。不会扫描或下载整个曲库。

这比旧实现少一首主动 ahead，并补上了准入预留、动态降额、重试预算、启动清理和最终提交
复核。网易云音乐的稀疏分段模型更节省“只听过一部分”的占用，但需要 Range 缺口调度、
区间索引和随机读取协议；Cadilume 当前的 Symphonia 渐进 Reader 依赖连续文件前缀，不能
只改文件格式就安全照搬。该模型应作为独立的后续架构升级，而不是混入本轮容量修复。

## 本机网易云音乐观察

本机安装的是网易云音乐 macOS `3.1.10`（Bundle ID `com.netease.163music`）。在线播放
缓存位于：

```text
~/Library/Application Support/com.netease.163music/Caches/online_play_cache
```

每个媒体身份对应三类文件：

| 文件 | 本机可观察作用 |
| --- | --- |
| `.uc!` | 具有完整媒体逻辑长度的稀疏文件，只有已缓存区间实际占用磁盘块 |
| `.idx!` | 明文 JSON，包含媒体逻辑 `size` 和已缓存连续区间 `zone` |
| `.info` | 独立、不透明的元数据；本轮不解码其内容 |

现场三个 `.uc!` 的逻辑大小合计 `123,528,193` 字节，连同索引/元数据后的文件逻辑大小为
`123,531,957` 字节；`du` 实际占用约 `65.6 MiB`。对应 `.idx!` 中两首只保存了开头区间，
另一首区间覆盖完整文件。这说明它能保留逻辑地址空间和区间索引，而不要求先写满整首。

这套模型适合按需 Range、快速 seek 和断点续传，也能减少跳歌后的浪费；代价是播放器必须
知道哪些区间存在、遇到缺口如何发起请求、多个 read head 如何合并、何时校验并提交完整
媒体。Cadilume 当前只在连续前缀达到 256 KiB 后启动解码，若直接制造稀疏洞，Symphonia
可能把未下载区域当成真实零字节或损坏数据，因此本轮不采用。

## 为什么 14 个音频会占 491 MB

Cadilume 的“原始质量”直接保存 PMS 返回的源文件；FLAC、ALAC 或高规格无损曲目单首
几十 MiB 很常见。`491 / 14` 约为每个文件 `35 MiB`，与完整无损曲目的量级一致，不是缓存
重复膨胀的直接证据。

旧流程会保存当前曲目、真实下一首，并机会性暖缓存下下首；连续播放后，已经听过的文件按
LRU 留在磁盘以便重播，所以数量会随收听累积。本轮已删除“下下首”预取：现在主动范围只有
当前曲目和可选的真实下一首，计数最多会比实际已经听到的曲目多一个。代码中没有遍历资料库
或整条队列下载的路径。

## Cadilume 当前预算模型

| 维度 | 本轮实现 |
| --- | --- |
| 用户上限 | 默认 1 GiB；设置中可选 1–10 GiB，持久化到 Rust 配置 |
| 主动下载范围 | 当前曲目；开启预缓冲时再加真实下一首，不再预取下下首 |
| 准入 | 有 Content-Length 时先为完整目标预留；未知长度时约每 1 MiB 复核 |
| 占用统计 | 完整 `.audio` 与下载中 `.audio.part` 全部计入同一上限 |
| 重试 | 原位覆盖同一个 `.part`；准入时排除将被覆盖的旧部分，避免把自身计算两次 |
| 动态降额 | 下载读取实时上限；已知长度目标在下一块写入前重新预留；取消推测性预取；提交前再次复核实际总占用 |
| LRU | 只删除最旧完整文件，保护当前播放和已预排下一首，不删除活动 `.part` |
| 启动 | 删除崩溃遗留 `.part`，再按已保存上限收口完整缓存 |
| 清理 | 停止 Rust 播放和下载，清空前端/Rust 队列与持久化会话，再删除封面和音频缓存 |
| 设置展示 | 封面缓存一行、音频缓存一行；音频显示总占用/上限、完整文件数和下载中数量 |

容量准入按下列顺序执行：

```text
读取最新上限
  -> 统计完整文件 + 其他活动 .part
  -> 加上本次即将写入的大小
  -> 超额则按 mtime 淘汰未受保护的最旧完整文件
  -> 仍无空间则拒绝下载/提交
  -> 成功下载后原子 .part -> .audio
```

这个模型有意允许一种短暂状态：用户调低上限时，当前播放文件、已挂接的下一首或正在取消
的 `.part` 可能暂时让状态显示超过新上限。Cadilume 不会为追求数字立即达标而删除播放器
仍在使用的文件；它会阻止新提交，并在任务退出或曲目不再受保护后继续 LRU 收口。

## 后续优化边界

若以后需要在低磁盘设备上进一步降低跳歌浪费，应单独实现“分段/稀疏缓存 v2”：Range
请求、区间合并索引、缺口感知 Reader、seek 优先级、崩溃恢复、校验与 LRU 以实际分配块
计费。完成这些门禁前，完整文件 LRU 更可审计，也更符合当前 gapless 下一首必须完整预解码
的约束。

离线下载也应保持独立：由用户显式选择项目、展示预计大小和进度、允许暂停/删除，并采用
自己的容量与保留规则；不能把流式缓存悄悄提升为离线资料库。
